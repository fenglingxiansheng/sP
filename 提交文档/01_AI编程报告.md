# AI 编程报告：豆绘 · 拼豆图纸工作台

整理日期：2026-10-13。范围：本次本地 Demo 的规划、实现、验证与反馈迭代。

## 1. 项目结果与技术组成

工具将用户上传的图片转换为拼豆图案，匹配真实 Artkal S 色号，支持编辑、用量统计和带网格/色号的 PNG 下载。项目使用 Vue 3、JavaScript、Vite 与 Canvas；全部图片处理在浏览器内执行。自动动漫抠图使用 Anime Segmentation 的 ISNet ONNX，由 ONNX Runtime Web 在 Worker 内推理。

本次交付为本地 Demo，未部署线上站点，也未上传 GitHub。当前实现范围和限制见 [功能与验收说明](03_功能与验收说明.md)。

## 2. 使用了哪些 AI 工具

| 工具 | 实际用途 |
| --- | --- |
| Codex 当前会话 | 澄清需求、拆分模块、编写与修改代码、检索官方资料、运行命令、设计验证脚本、整理文档 |
| Anime Segmentation / ISNet | 产品运行时的动漫主体分割模型，浏览器本地执行；不是编程助手 |
| U2NetP | 早期自动抠图方案，真实使用后因效果不足被 ISNet 替换为非默认历史模型 |

协作中使用过 codebase-design 的模块设计指导、Sites 的本地实现与验证指导，以及 diagnosing-bugs 的复现与诊断方法。未使用子代理并行开发，未使用 AI 图片生成工具，未调用远程图片抠图服务。没有可靠记录证明底层模型的精确版本，故不虚构具体 GPT 型号。

开发辅助工具为 PowerShell、Node/npm、Python、Chrome 和临时 Playwright 自动化。Python 用于色表数据整理、样例/文档/打包等开发工作，不是网页运行依赖；Playwright 用于开发期间冒烟检查，不要求验收者安装。

## 3. 如何与 AI 协作

### 先澄清，再写代码

用户最初明确要求“先不要着急写代码”，先确定模块、素材、接口与流程，并要求方向问题询问。AI 分批确认交付时间、功能范围、浏览器本地处理、前端框架、拼豆品牌、界面布局、导出格式及项目保存规则。用户将原生 JavaScript 方案改为 Vue / React，最终选择 Vue 3；接受 Artkal S、浅色三栏布局、PNG 导出，不做 PDF。

在用户明确提出“按照这个设计md文件分模块编写代码出一个demo”后，AI 才推进实现。用户负责产品范围和验收方向，AI 负责实现细节与基础验证。Node/npm 与依赖锁定用于复现环境，前端项目使用 package-lock.json，而不是无用途的 Python requirements.txt。

### 按模块推进，并用真实操作反馈修正

实现按色表、图像采样、色差匹配、编辑历史、项目文件、PNG 导出、Vue 工作台组织。Canvas 负责显示，格子色号数组作为图案事实来源；统计、保存和导出读取同一数据，避免只改画面没有改结果。

用户随后通过实际使用不断明确需求：

1. 指出缺少128快捷尺寸和主体裁剪，新增原图裁剪草稿与非破坏采样。
2. 提出按底板控制颗数，确认29×29底板、1/4/9块组合和保持比例；增加宽高滑块与三种像素化方式。
3. 背景处理先按用户确认做纯色去除与手动擦除/恢复，再经明确确认增加浏览器本地自动抠图。
4. 用户反馈轻量模型效果不好，提供 Anime Segmentation 源码目录；AI 读取其推理和导出代码，接入官方 ONNX 权重。
5. 用户提交手臂误删案例，AI 用同一原图复现并读取概率，增加点选保留和原图参考辅助修补。
6. 用户提出类似 Photoshop 的查看方式，新增 Ctrl＋滚轮、空格拖动，验证视图操作不误修改数据。

这种流程不是一次提示后直接交付：用户通过具体图片与操作提出修正，AI 将反馈转成可测试的行为，再返回已实现范围与尚存限制。

## 4. 难点一：真实拼豆色号与可重复匹配

**问题：** 品牌页面标称色数并不等于可直接使用的 RGB 记录数；官方表包含无数值的金属色，还存在不同色号具有相同 RGB 的情况。随意补值会让导出图纸看似完整，却无法可靠对应真实颜色。

**用户输入与上下文：** 用户询问“色盘匹配这个功能目前打算要怎么实现 需要我寻找一些目前网络上的拼豆套装嘛”。结合此前接受 Artkal S 的选择，AI 将目标明确为真实品牌色表，而非虚构通用颜色或声称覆盖某一具体套装。

**处理：** 从官方 RGB PDF 提取 S01～S159 的数值，排除没有 RGB 的 S41/S42/S63，保留156色，并记录出处和原文件校验值。像素按 sRGB 转换到 D65 Lab，以 CIE76 选择最近色；距离相同按色表顺序固定选择，其他真实色号仍可手工选取。

**验证与限制：** 测试色号唯一性、颜色范围、精确颜色匹配和相同RGB的确定性；导出色号来自同一图案数据。数字色表不等于实物测色，屏幕和实体豆存在差异，项目没有品牌官方背书。

## 5. 难点二：自动抠图效果不佳，如何定位并诚实迭代

**问题：** 最初为了浏览器体积与运行成本选择轻量 U2NetP。用户实际反馈不理想后，指定 Anime Segmentation。更换模型不能只换文件路径：旧模型与 ISNet 的输入尺寸、归一化和输出处理不同。

**用户提供的上下文：** 用户提供本地 `chunk_photo/anime-segmentation-main` 源码；AI 阅读 `inference.py` 和 `export.py`，按1024×1024等比例居中补边、RGB除以255、输出去补边与还原尺寸接入。模型固定官方版本，校验SHA256；176 MB权重用下载脚本准备，避免作为普通GitHub文件提交。

**进一步反馈：** 用户指出深色手臂被判成背景，并提供原图/结果图。AI 在同一原图复现：两侧手臂采样点被删除，脸部保留。诊断发现袖子前景概率约0.00514和0.00139，一处真实背景约0.04144；所以全局降低0.5阈值无法同时可靠保留袖子并去掉这处背景。

**处理：** 没有将“模型能运行”当作“分割准确”，也没有声称阈值调整解决漏识别。增加按原图连通近似颜色的“点选保留”、淡显原图参考，以及已有恢复/擦除笔刷。每次点选可撤销，参考层不参与导出。

**验证与限制：** 模型在开发版和生产版真实推理通过；上游动漫单样例首轮约8～11秒，仅是本机单次观察。手臂采样点在辅助恢复后保留，背景抽查点保持删除，但完整袖子仍需修边，高容差可能带回背景。自动模型漏识别问题尚未彻底解决，辅助修补只是降低修改成本。

## 6. 验证结果

- 最新24项 Node 核心自动测试通过，生产构建通过。
- 已用浏览器检查上传、生成、编辑、撤销/重做、项目保存/恢复、PNG导出、透明图片、128×128输出、裁剪及尺寸预算。
- 背景处理检查包括纯色连通区域、内部同色保护、笔刷恢复、模型实际推理、取消和模型缺失时保留原有修改。
- 两个图片窗口检查了鼠标锚点缩放、空格平移、复位，以及视图操作不改变裁剪/蒙版/历史、松键后继续编辑。

这些是已做的基础验证，不代表完整跨浏览器、所有真实图片、长期内存、移动端手势或无障碍验收。后续完整接口与功能测试由用户安排。

## 7. 协作复盘

有效的输入不只是功能名，而是“用户遇到了什么问题”：背景浪费豆子促成裁剪和蒙版；底板数量促成尺寸预算；手臂误删案例促成概率诊断与交互修补；查看不便促成快捷缩放和平移。AI 适合快速拆分、实现与验证，但素材相关的视觉质量必须回到真实样例判断。

下一步若继续提升自动抠图，应建立包含困难姿势、深色服装、多个角色的真实样例集，比较不同模型或可提示分割，而不是凭单张成功图片宣称整体改善。
